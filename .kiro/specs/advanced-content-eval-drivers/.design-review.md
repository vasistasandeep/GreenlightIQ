# Design Review — Advanced_Content_Eval_Drivers

Reviewer: design-review subagent (fresh read, no authoring context).
Scope: `design.md` reviewed against `requirements.md` for a spec-documents-only feature. No build/tests run (there is no implementation). The design's claims about existing code were verified by reading the referenced source.

## Verdict

**CHANGES_REQUESTED** — 1 HIGH, 2 MEDIUM, 3 NIT. (Verdict is mechanical: any HIGH/MEDIUM blocks.)

The design is unusually thorough and almost all of its claims about the existing codebase check out exactly. The blocking findings are about a normative contract the design unilaterally changes relative to the requirements (the momentum term), one unquantified clamp-composition claim for the momentum multiplier, and an under-specified churn-side attribution-order statement. None of the locked decisions are reopened; the worked numeric example conserves to the exact Decimal; the pgvector query, staleness rules, STAGE_EXCLUDED neutrality, and the Hypothesis property list are all present.

## Findings

### 1. [HIGH] The design silently supersedes a normative requirements identity (the momentum term) instead of forcing the requirements to be corrected first

**Where:** "The combined log-space model" → the "Deviation from R5.1 / R5.2 / the Attribution_Order glossary" callout; "Normative application / attribution order"; and the conservation identity throughout.

**Problem.** Requirement 5.1 defines `y_log = ln(1 + H_comps) + Σ(βᵢ·xᵢ) + ln(M_window) + ln(M_ip) + ln(M_vernacular) + ln(M_calendar)`, R5.2 states the matching six-term-plus-residual conservation identity, R5.4 fixes the six-stage Attribution_Order, and the glossary `Attribution_Order` repeats it — all **without** a momentum term. Requirement 3, however, requires a `Momentum_Multiplier` that multiplies the full prediction. The requirements are therefore internally inconsistent (R3 needs a multiplier that R5.1/R5.2/R5.4 have no slot for). The design resolves this by inserting `ln(M_momentum)` as Stage 2 and declaring "This design's seven-term order supersedes the momentum-free order in the requirements."

A design document cannot, on its own, make a normative requirements identity (R5.1/R5.2/R5.4, acceptance criteria) non-binding. Downstream, the implementer must satisfy *both* documents; right now they conflict on the single most audit-critical contract (the conservation identity and the attribution order). A reviewer reading only these two documents cannot tell which identity is authoritative without the design arrogating that authority to itself.

**Fix (choose one, then make the two documents agree):**
- Preferred: raise a one-line requirements erratum adding the `ln(M_momentum)` term to R5.1, R5.2, R5.4, and the glossary `Attribution_Order` (as Stage 2), then change the design callout from "this design supersedes the requirements" to "aligned with R5.x as amended by erratum <id>." This is the cleanest and matches the design's own stated position.
- Alternative: if momentum must not enter the hour-space product (e.g. keep it a pure UI/telemetry signal), then Driver C does not belong in the `y_log` identity at all and the design's Stage 2 must be removed — but that contradicts R3.2/R3.5, so it is the weaker option.

Until the two spec documents state the same normative identity, this is a blocking conflict, not an editorial note.

### 2. [MEDIUM] The Momentum_Multiplier clamp band `[1.00, 1.50]` is asserted by the design but has no basis in any requirement, and R3.5 only mandates `>= 1.00`

**Where:** "Driver C — Momentum_Telemetry" → `Momentum_Multiplier = clamp(raw, 1.00, 1.50)`; Hypothesis Property 3 ("momentum [1.00,1.50]"); the explanation JSON `"bounds": "[1.00,1.50]"`.

**Problem.** R3.5 requires only that the composed multiplier be "bounded at or above 1.00 when active" — it specifies the *lower* bound (1.00) and the monotonicity direction, but states **no upper bound**. The design introduces `1.50` as the inclusive upper clamp and then asserts it as a Hypothesis-tested invariant. The task prompt's blocking list explicitly calls out "windowing/IP/vernacular stated domains" and the other multiplier clamps as things that must be *stated and self-consistent*; the momentum upper clamp is neither derived from a requirement nor justified in the design (unlike, say, `S_velocity [0.50,2.00]` which is lifted directly from R3.2, or seasonality `[0.80,1.35]` from R4.3). A fixed `1.50` ceiling is a real modeling decision (it caps how much any produced-title buzz can lift the prediction) presented as if it were given.

This also interacts with the composition formula: `raw = 1 + 0.15·norm(V_trailer) + 0.20·E_ratio + 0.25·(S_velocity − 1)`. The design never defines `norm(V_trailer)`'s range or `E_ratio`'s range, so it is not shown that `raw` actually stays meaningful against the `[1.00, 1.50]` clamp (e.g. whether the clamp is routinely saturated, which would make the three weights cosmetic).

**Fix.** Either (a) add an explicit, justified momentum upper-bound coefficient to the `momentum` sub-object (e.g. `momentum_multiplier_max = 1.50`) and state the empirical rationale the same way Driver D states its domains, and define the input ranges of `norm(V_trailer)` and `E_ratio` so the clamp's role is clear; or (b) if no upper bound is intended, drop the `1.50` ceiling and clamp only at the `>= 1.00` floor per R3.5, adjusting Property 3 accordingly. Pick one and make the formula, the clamp, the Hypothesis property, and the explanation `bounds` string all agree.

### 3. [MEDIUM] The churn-side attribution order is stated as "fixed and normative" but is never defined as an ordered sequence the way the hours side is

**Where:** "Churn-space conservation" → identity `C_comps_anchor + Σⱼ(feature_pointsⱼ) + delta_C_franchise + bounds_adjustment == final_churn`; and "Application order on the churn side is fixed and normative: `delta_C_franchise` is applied **before** the `[0.10, 5.00]` clamp and the 1.5 hurdle."

**Problem.** The hours side gets a fully specified 7-stage sequential re-exponentiation order because multiplicative Decimal deltas do not commute. The churn side is purely **additive** (every term is a pct-point addend, as confirmed in `churn.py`), so summation *does* commute and the only order that matters is "credit before clamp before hurdle" — which the design states. But the design calls the churn order "fixed and normative" and lists `C_comps_anchor + Σⱼ(feature points) + delta_C_franchise + bounds_adjustment` as if the sequence of the additive terms were itself a contract, without saying it is order-independent. That ambiguity invites an implementer to treat the *listing order* of the additive terms as significant (it is not) or to wonder whether `delta_C_franchise` is summed before or after the per-feature points (it commutes, but the 2 dp `_quantize`-per-line residual in `bounds_adjustment` could differ if someone quantizes `delta_C_franchise` at a different point than the feature points).

`churn.py` quantizes each contribution to 2 dp individually and reconciles the whole in a single `bounds_adjustment`. The design must say explicitly that `delta_C_franchise` and the new `comps_anchor` line are each quantized to 2 dp the same way, and that only the *clamp/hurdle position* is normative (additive summation commutes), so `bounds_adjustment` remains the sole residual at 2 dp.

**Fix.** Replace "Application order on the churn side is fixed and normative" with: "The churn model is additive, so the summation of the `comps_anchor`, per-feature, and `franchise_loyalty_credit` lines commutes; each line is quantized to 2 dp (`_Q`, ROUND_HALF_UP) exactly as the existing churn contributions are, and `bounds_adjustment` carries the single reconciliation residual. The only normative ordering is that `delta_C_franchise` is summed into the unclamped total *before* the `[MIN_CHURN, MAX_CHURN]` clamp and the 1.5 hurdle / BORDERLINE_BAND classification." That removes the false parallel to the non-commuting hours order while keeping the one constraint that actually matters.

### 4. [NIT] `norm(V_trailer)` is referenced in the momentum formula but never defined

**Where:** "Driver C — Momentum_Telemetry" → `raw = 1 + w_v * norm(V_trailer) + ...`.

**Problem.** `V_trailer` is defined ("first-72h organic views / trailer marketing budget"), but the normalizer `norm(·)` that maps it into the composition is undefined — its output range, whether it is genre-relative, and what a neutral `V_trailer` yields are all unstated. This is a smaller instance of Finding 2 and is only a NIT because the momentum driver ships DETERMINISTIC_FALLBACK and is flag-off by default, so it cannot affect the demo. It still must be defined before Driver C can be implemented.

**Fix.** Define `norm(V_trailer)` concretely (e.g. `norm(V_trailer) = clamp(V_trailer / baseline_V, 0, cap)` with the baseline and cap as named DETERMINISTIC_FALLBACK coefficients) so the composition has no free symbol.

### 5. [NIT] `release_month` neutral default is NULL but R8.4 asks for "an explicit neutral default that yields a 1.00 multiplier"

**Where:** "Data model changes" → `release_month | integer | NULL (neutral -> 1.00)`; migration `op.add_column("titles", sa.Column("release_month", sa.Integer(), nullable=True))` (no server_default).

**Problem.** Every other new Driver-D column has an explicit server-side default (`source_ip_provenance='ORIGINAL_SCREENPLAY'`, `release_window='DIRECT_TO_STREAMING'`, `vernacular_track_count='1'`). `release_month` is nullable with no `server_default`, relying on the resolver mapping NULL → 1.00. R8.1/R8.4 require "an explicit neutral server-side default." A nullable column with no default is defensible (NULL is unambiguous and the resolver treats it as neutral), but it is inconsistent with the sibling columns and with the literal wording of R8.4. The byte-identity argument still holds (NULL → 1.00 seasonality), so this does not threaten the demo.

**Fix.** Either add `server_default=sa.text("NULL")` and state that NULL is the explicit neutral sentinel (resolver maps NULL → 1.00), or give it a concrete neutral integer default and document the month→multiplier map so that default demonstrably yields 1.00. Make the data-model table and the migration say the same thing.

**Where:** "Responses to design review findings" — "how each finding from the current `.design-review.md` / `.design-review.json` (CHANGES_REQUESTED, 2 HIGH / 2 MEDIUM / 2 NIT) was resolved."

**Problem.** This is a provenance/traceability note, not a design decision, and it embeds a snapshot of a previous review's counts inside the normative design document. ## Unverified / Wrong Assumptions

- **No wrong assumptions found.** Every claim the design makes about existing code was checked against the source and matched.
- **Unverified (out of scope to confirm from spec docs, flagged by the design itself):** the Driver-C precondition that the telemetry cache writer re-stamps `last_updated_at` on every poll. `last_updated_at` is a creation default (`created_at_column()`, no `onupdate`), so the 14-day staleness clock is only meaningful if the upsert path updates it. The design correctly states this as an out-of-scope precondition; it cannot be verified from the spec documents and must be ensured when the cache-writer path is implemented (future work).
- **Unverified:** the demo byte-identity claim ("the five seeded titles recompute identically with all flags false") is argued soundly from the neutral defaults but cannot be executed here (spec-docs-only, no implementation). The argument is logically complete: flags false → each driver inert → `H0 = exp(intercept) - 1`, no franchise floor/credit, momentum 1.00 (STAGE_EXCLUDED), all Driver-D multipliers 1.00.
